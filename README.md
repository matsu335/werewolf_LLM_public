# Werewolf LLM Lab

HumanとLLMが同じ村に参加できる、ローカル実行型の人狼ゲーム兼AI実験基盤です。ゲーム上の真実は決定論的なゲームエンジンが管理し、LLMは判断だけを行います。

目的は「ルールだけを与えたときLLMが何をするか」の観察です。人間が蓄積した人狼の戦略（「人狼はCOするな」「狩人から襲え」など）はプロンプトに入れません。入れると、測っているのがLLMの判断なのか人間の知識なのかを区別できなくなります。ルールや仕組みの説明は入れますが、戦略の指示は入れません。

## 起動

必要環境は Node.js 24 以降です。外部npmパッケージは使用していません。

```powershell
npm start
```

ブラウザで `http://127.0.0.1:3000` を開きます。データは `data/werewolf.sqlite` に保存されます。

Ollamaを使う場合は、Base URL（既定 `http://localhost:11434/v1`）とインストール済みのモデル名（例 `qwen3:8b`）を各AIに設定してください。APIに接続できなくても、Retry後に安全なFallbackを使ってゲームは進行します。

既定の村は5人（人狼1・狂人1・占い師1・狩人1・市民1）で、部屋の人数は最大9人です。人狼が1人の村では人狼会議と作戦メモは発生しません。

### OllamaはネイティブAPIで呼ぶ

Base URLがOllama（`localhost:11434`）のときは、OpenAI互換の `/v1/chat/completions` ではなくネイティブの `/api/chat` を使います（設定 `api`: `auto` / `ollama` / `openai`）。OllamaのOpenAI互換エンドポイントは `num_ctx` を無視し、コンテキスト4096でモデルを読み込み直して、**入力の先頭側を黙って切り捨てます**。Ollama 0.34.4で約12,400トークンの入力を送った実測では、`/v1` は2,050トークンしか評価しませんでした（`num_ctx` を指定しても同じ）。ネイティブAPIは同じ入力を12,415トークンすべて評価して正答しています。過去の9人卓のログでも、67302c03は133件中91件、6f86d3b6は144件中58件の呼び出しがちょうど2,050トークンでした。つまりそれらの試合でモデルは入力の大半を見ていません。

ネイティブAPIでも送る内容と拘束は同じです。JSONスキーマは `format`、出力上限は `options.num_predict`、コンテキスト長は `options.num_ctx`、温度とseedは `options` に入れます。

### LLM出力とコンテキストの扱い

出力予算はCall種別ごとに分けています（投票は320トークン、発言は800トークンなど）。理由文が長くなって末尾が切れ、JSONが壊れるのを避けるためで、各Promptにも文字数上限を明記しています。

思考は禁止していません。`/no_think` は使いません。`private_thought` フィールドを持つ呼び出し（CO判断と発言）では、考えたことをそこへ短く書かせ、その内容は他プレイヤーへ公開しません。このフィールドを持たない呼び出しの出力規則にはこの一文を載せません（載せると存在しないフィールドを指すことになります）。

そのため、送る `max_tokens` はJSON本体の予算に思考枠 `reasoningTokens`（既定4096）を上積みした値にしています。Qwen3のような推論モデルは思考をJSON本体より先に出力し、その思考は `content` ではなく別フィールド（ネイティブAPIでは `message.thinking`、OpenAI互換では `reasoning`）で返ります。本体の予算だけで送ると、思考を書き終える前に長さ上限に達し、`content` が空のまま `finish_reason: "length"` で返ってきます。既定値はqwen3:8bの実測（思考が最大12,700文字、英語で約3,200トークン）に合わせています。思考の全文はログの `reasoning` に保存し、メトリクスの「思考だけで枠を使い切った率」で設定の妥当性を確認できます。

### Retryの方針

Retryは同じ入力の投げ直しではなく、前回の出力と却下理由を渡した修復依頼として送ります。ただし**推論を減らすことは決して依頼しません**。これは実験の妥当性に直接関わります。qwen3:8bで「考える量を減らし、先にJSONを書いてください」と促した結果、推論を伴わない定型出力がそのまま本番の発言・投票として記録されました。プレイヤーを `A`・`B`・`J` と呼ぶ襲撃指示が出て、それが作戦メモへ転記されて翌日の入力に戻り、ある日の投票7票のうち5票が「人狼の行動に疑いあり」程度のほぼ同一の理由で、発言録に最も多く登場するIDへ集まりました。観察対象がモデルの判断ではなく修復ループの副作用になってしまいます。

そのため失敗の種類で扱いを分けます。出力枠の使い切り（`content` が空）はモデルの判断の問題ではなく予算の問題なので、**何も指摘せず**思考枠を倍にして同じ問いを出し直します。上限は入力を差し引いた残りコンテキスト（最大8192トークン）です。検証による却下の場合は、前回の本文を1200文字まで添えて「判断の中身は変えず、指摘だけを直す」よう求めます。候補外の対象を選んだ場合は、却下理由に選べる候補の一覧を含めます。候補を示さずに「含まれていません」とだけ返していたころ、モデルは「validTargetsが与えられていない」と推論し、プロンプトの例示 `"reason":"日本語80文字以内の理由"` をそのまま写して返しました。例示値は `<…>` で囲んだ形に改め、それをそのまま返した場合は差し戻します。言語違反も書き直しではなく翻訳として扱います。作り直させると論拠が落ちた一行に縮むためです。

### 入力は読める説明文で渡す

LLMへの入力（user メッセージ）は、構造化データを `src/llm/input-renderer.js` で見出し付きの説明文に描き起こしたものです。「あなたは誰か」「現在の状況と配役」「プレイヤー表（生死・現在のCO）」「これまでの公開記録（起きた順）」「あなただけが知っている情報」「人狼会議（該当時）」「今回選べる相手」の順に並べます。

以前は入力を `JSON.stringify` したものをそのまま渡していました。4人卓のログ（bae474a7）では、狩人が前の話者（人狼）の発言を思考の中で "the user's example" と呼び、「P1が怪しい。襲撃対象にすべき。」を一字一句写して自分の発言にしていました。発言録のJSONを出力例として読んだためです。夜行動の語彙「襲撃」はその人狼が捏造された作戦メモ（下記）から持ち込んだもので、狩人はそれを写していました。

公開発言は初日から全文を渡します。古い日を件数だけの要約に落とすと、モデルの視界が黙って削られるためです。

### 名乗りとCO

役職の主張はCO操作で行います。公開発言の中で役職を名乗れるのは、いまCOしている役職だけです。禁じているのは「COをせず、発言の中だけで役職を主張する」ことで、COしている役職を発言でも名乗ることや、「私は人狼ではない」のような否定は許します。COと食い違う名乗りを含む文は差し戻し、最終手段ではその文だけを落として残りを活かします。

### 作戦メモは会議があったときだけ

人狼会議は狼が2人以上のときだけ開きます。作戦メモ（会議の要約）も、会議が開かれ発言が1件以上あったときだけ更新します。以前は狼が1人でも「会議を要約せよ」と呼んでいて、盤面も配役も入力に無いため、モデルはルールブックの役職一覧から「狂人を襲撃する」という計画を捏造しました。その卓に狂人は0人です。この捏造メモが以降すべての狼の呼び出しに載り、初日のCO判断まで汚染しました。現在の作戦メモ更新には、会議の発言に加えて盤面と自分の情報も渡します。会議の無い夜に、前回の会議の内容を今夜のものとして渡すこともしません。

### 何を選ぶ場面かをキー名で区別する

対象を1人選ぶCallは、種別ごとに別のPromptと別の出力キーを使います。投票は `execute_target`、襲撃は `attack_target`、占いは `divine_target`、護衛は `guard_target` です。

以前はすべてが `{target, reason}` という同じ形で、夜行動のPromptも1ファイルを共用していました。qwen3:14bのログでは、狩人が処刑投票の `target` に護衛したい相手を書き込んでいました。理由欄は「P7は狩人として、P1への支持の多さからP4を守ることを決めた」、その思考には「狩人として誰を守るかを決める課題だ」とあり、これは投票Callの最中の出力です。同じことを他の3人もしていて、初日に占い師の白先が4票で処刑されました。人狼と狂人の票は1票も入っていません。誰を選ぶかの判断ではなく、何を選ぶ場面かの取り違えです。各Promptには帰結も書いています（投票なら「最多票の1人がその場で処刑され、ゲームから永久に除外される」）。別の行動のキーで答えた場合は場面の取り違えとして差し戻します。

### Claimは発言と対応していなければならない

`claims` は発言とは別に全員へ公開されるチャンネルです。そのため、発言本文で触れていない占い結果・護衛をClaimだけで配ることを禁止しています。`divination_result` と `guard` のClaimは、その対象IDが発言本文に現れていなければ差し戻します。

qwen3:14bのログでは、占い師が初日の発言で占い結果に一言も触れないまま `divination_result P4 not_werewolf` をClaimで全員に配っていました。発言を読んでも誰も反応できないのに、公開情報の上ではP4が白として扱われます。Claimの真偽はゲームが検証しないので（どの役職でも偽の占い結果を出せます）、これは嘘を封じる検査ではなく「主張は公開の場で述べる」というルールの検査です。疑い・信頼のClaimは意見であって役職由来の情報ではないので、本文との対応までは要求しません。表記の揺れ（「白」「人狼ではない」「not werewolf」）は `not_werewolf` / `werewolf` の二値へ揃えます。

### 役職の能力は共通知識

`rules/rulebook.md` に全役職の能力を明記しています。誰がどの役職かは秘密ですが、各役職に何ができるかは人間の卓では全員が知っている情報です。Promptの構成上、各プレイヤーには自分の役職ファイルだけが渡るため、以前は人狼が「狩人は襲撃を防げる」ことをどこからも知りませんでした。qwen3:14bのログでは、狩人がCOしている状況で人狼が初日に占い師を襲撃し、思考の中に護衛を警戒した検討が一度も現れませんでした。これは戦略の注入ではなくルールの欠落の修復です。配役の人数（`roleCounts`）は以前から公開情報として渡しています。

### コンテキストに収まらない入力は送らない

公開発言を全日全文で渡すので、入力は日を追うごとに増えます。入力を黙って削ることはしません。

- 試合開始前に、最悪の場合（毎日1人が処刑され夜の死者が出ず、生存者3人まで続く）の入力量を見積もり、各AIの `contextTokens`（既定16384。Ollamaには `num_ctx` として送る）に収まらない設定では開始しません。部屋作成画面に見積りを表示します。
- 呼び出しのたびに、送る全メッセージのトークン数を見積もります。必要量（入力＋出力枠＋思考枠）が8割を超えたらログ・ステータス・メトリクスに記録し、上限を超えたら**送らずに試合を終了**します（`ContextOverflowError`）。Fallbackで続けると無作為な投票や行動が混ざり、観察対象がモデルの判断ではなくなるためです。
- 実際に評価されたプロンプトトークン数が送った量を大きく下回った場合は、推論サーバ側の切り捨てを疑ってログとメトリクスに記録します（ネイティブAPIに切り替えた後も検知は残しています）。

`llm.seed` は既定で固定値です。未固定だと同じ局面を再現できず、観察結果を比較できません。

ルール単体テストに加え、すべてのLLM Callが失敗する条件でも全AIゲームが終了し、Fallbackと内部状態がSQLiteに記録される統合テストを含みます。

## 構成

- `src/domain/`: LLMから独立したゲームルール、設定検証、Seed付き乱数
- `src/app/`: フェーズ進行、Human待機、AI同時判断スナップショット
- `src/llm/`: OpenAI互換Client、Prompt構築、Retry/Fallback
- `src/storage/`: SQLiteイベント・LLM Call・内部状態履歴
- `config/ja/`, `config/en/`: 編集可能なルール、役職説明、Call別Prompt（日本語版と英語版）
- `public/`: 部屋作成、リアルタイムゲーム、AI状態、終了後分析GUI（`llm-view.js` はLLM入出力の表示、`translation.js` は観察用の日本語訳）
- `test/`: エンジン単体・全AI障害統合テスト

## データと秘密情報

イベントの可視性は `public` / `secret` / `system` の3種です。`system` はLLM Callの進捗などの運用テレメトリで、参加者ビューにもLLM入力にも載せません。`callType` から夜の役職行動（attack=人狼、divination=占い師、guard=狩人）が割れてしまうためです。

LLMへ渡す公開情報は生イベント列ではなく、`publicBrief()` が返す正規化ビュー（座席と生死、現在のCO、公開された出来事を起きた順に並べた記録）です。人間が画面で見ているものと等価な情報だけを渡します。秘密情報として渡すのは、エンジンが書く `privateInfo`（占い結果・護衛履歴・仲間・自分の投票と襲撃投票）と作戦メモだけです。

CO操作は「その役職だと主張している」という記録で、適用されなかった役職名は記録にも公開イベントにも残しません。`type` が `none` のときに役職名を書いても無視されます。

公開発言で名乗れる役職は、いまCOしている役職だけです（上記「名乗りとCO」）。検査に通らなかった発言は、該当する文だけを落として残りを活かします。空発言は「黙っている＝怪しい」という偽の推理材料を生むため、最終手段でも保留発言を入れます。

ゲーム中の通常ビューには公開イベントだけを表示します。Humanの操作対象を選択したときだけ、その本人の役職・秘密情報を表示します。終了後のResearch dataでは、真の役職、秘密投票、夜行動、作戦メモ、LLM入出力を含む全データをGUIまたはJSONで確認できます。

## 実験メトリクス

終了後のResearch dataの「実験メトリクス」、または `GET /api/games/:id/metrics` で次を確認できます。

- JSON成功率、失敗数、Fallback数、Call種別ごとの内訳
- 出力が長さ上限で切れた率、思考だけで枠を使い切った率、思考の最大文字数
- 入力の切り捨て疑い率、必要量がコンテキストの8割を超えた率、最大入力トークン数（推定と評価値）・文字数
- 公開ビューへ漏れた `system` イベント数、未適用の役職名を載せたCO数、空発言数
- CO総数、真の役職と一致したCO数、人狼が人狼COした数、CO済みの人物が処刑された回数

ゲーム途中からの再開と複数試合バッチは初期対象外です。アプリ再起動後も終了済み・過去ゲームの閲覧とExportは可能です。

## Game / Game-view

- `Game`は参加者向けの公開情報ビューです。発言順を基準にプレイヤーを円環配置し、現在の行動者を赤枠、直近の発言・COを吹き出しで表示します。公開タイムラインは円環UIの下に表示します。
- `Game-view`は実験観察者向けです。同じ円環上に真の役職を表示し、人狼会議、秘密投票、夜行動、全LLM入出力をリアルタイムに閲覧できます。参加プレイヤーには見せないでください。
- Game-viewの監視チャットは、ゲーム中に起きたことを1本の時系列にまとめて表示します。公開発言とCOのほか、発言に付いたClaim、役職の配布、誰が誰に投票したか、占い・護衛・襲撃の選択とその結果、護衛で襲撃が空振りしたこと、そしてLLM呼び出しの試行1件ごとの送信内容・思考・出力・却下理由までを含みます。`公開` / `秘密` / `システム` / `LLM入出力` のチェックボックスで表示を絞れます。
- LLM呼び出しの「送信内容」は、HTTPで実際に送ったbody（`log.request`）をそのまま描いたものです。`messages` を `system` → `user（状況）` → `user（修復依頼）` の順に役割付きで全文表示し、LLMが読んだものと一字一句同じです。出力を拘束するパラメータ（`format` / `response_format` のJSONスキーマ、`num_predict`、`num_ctx`、温度、seed）も表示します。以前のログは system と入力を別々に持つだけで、監視チャットには入力（プロンプトの一部）しか描かれず、修復依頼は記録されていませんでした。旧形式のログはその旨を注記して表示します。
- 護衛が襲撃を防いだかどうかはゲーム上は誰にも公開されませんが、夜の因果を追えないと観察にならないため `attack_outcome` イベントとして記録し、監視チャットにだけ表示します。LLMへ渡る公開情報には含まれません。

## 比較条件

- `discussionMode`: `sequential` は順番に発言（直前の発言を読める）、`simultaneous` は全員が同一スナップショットから同時に発言します。逐次進行で観測される「前の話者への追従」が進行方式由来かモデル由来かを切り分けるための条件です。
- `wolfMeetingMode`: `sequential` は仲間の発言を読んでから応答、`independent_first` は互いを見ずに同時発言します。
- `language`: LLMとの共通言語（`en` / `ja`、既定 `en`）。プロンプト・ルールブック・役職文書・入力の説明文・却下理由・出力規則がすべて切り替わります。英語の方が安定するという見立てを実測で比べるための条件です。英語では発言などの長さを語数で指定します（発言100語、理由30語など）。同じ文字数の上限では、英語は日本語の約4割の情報量しか入らないためです。

### 言語ごとの検査

- 名乗りの検出は言語ごとに別の規則です。日本語は「私/俺/僕 + は/が/こそ/として + 役職語」、英語は「I am / I'm / my role is / I claim + （冠詞・強調・否定の許可リストの語だけ）+ 役職語」と「As the seer, I …」です。主語と役職語の間に別の述語が挟まる文（"I think P3 is the werewolf"、「私はP3が人狼だと思う」）は名乗りとみなしません。
- 発言の言語検査: 英語の試合では日本語・中国語・韓国語の文字を1字でも含めば差し戻します（qwen3は思考中に中国語を混ぜます）。日本語の試合では従来どおり日本語の文字を含むかだけを見ます。そのため中国語の文は通ってしまいます。

## 観察用の日本語訳

英語の試合では、公開発言・人狼会議・出力・思考・却下理由・修復依頼に日本語訳を付けられます。厳密な翻訳ではなく、何を言っているかを一瞬でつかむためのものです。訳文は画面表示と専用のキャッシュ（`translations` テーブル）にしか置かず、**ゲーム状態やLLMへの入力へは一切戻しません**。

- 翻訳はブラウザ内蔵の Translator API（デスクトップ版Chrome 138以降）を使います。端末内で処理し、外部へは送りません。初回だけ言語モデルのダウンロードが要り、翻訳ボタンのクリックで始まります。非対応のブラウザでは、サーバーに `DEEPL_API_KEY` を設定すればDeepL APIで翻訳します。
- 既定は「クリック時＋試合後に一括」です。Game-viewの監視チャット上部で「試合中も自動」に切り替えられます。
- LLMへの入力（system と user）は翻訳しません。同じ構造化入力を日本語のテンプレートと日本語版のプロンプトで描き直した「日本語版」を表示します。訳ではなく並行管理の原文なので、英語版と内容が揃っていることはプロンプトファイルの管理で担保します。

## 進行・終了操作

- ゲーム画面の「一時停止」は、Human入力待ちでは即時に停止します。LLM Call中はそのCallを完了し、次の安全な処理境界で停止します。
- 一時停止中は同じボタンが「再開」になります。
- 「強制終了」はその時点までのログを保存し、ゲームを終了状態にします。
- Archiveの「削除」は、対象ゲームのイベント、LLM Call、内部状態を含む全履歴を削除します。元には戻せません。
- 上部メニューの「システム終了」は、進行中ゲームを強制終了して保存した後、ローカルサーバーを停止します。再度利用する場合は `npm start` を実行してください。
